# ADR-002: Key Management

## Status

Accepted（Issue #138, #140, #174, #190 を実装の裏付けとして参照し、事後的に整理したADR。Issue #111 は関連する計画中の拡張として言及するが、本稿執筆時点では未実装（open）である）

## Context

初期の実装では、家族パスコードから導出した鍵で各レコードを直接暗号化する、マスターキー層を持たない構造だったと考えられる。この構造では、パスコード変更のたびに家族が保有する全レコードの再暗号化が必要になり、レコード数の増加に比例してパスコード変更のコストが増大するという課題があった。この課題は Issue #138「家族を変更せずにパスコードだけをローテーションできるようにする」として明示的に認識され、対応が行われている。

また、PBKDF2の反復回数を将来引き上げる際に、既存データとの後方互換性をどう保つかという課題も別途あり、これは Issue #140「PBKDF2 のイテレーション数をスキーマ管理する」として対応されている。

## Decision

Issue #138 への対応として、3層のエンベロープ暗号化を導入した。家族パスコードから PBKDF2-SHA256 で導出した鍵で家族共通のマスターキー（`families.masterKeyEncrypted`）をラップし、マスターキーで認証情報1件ごとに生成するDEK（`credentials[].passwordHintDekEncrypted`）をラップし、DEKでパスワードヒント本体を暗号化する。パスコード変更はマスターキーの再ラップのみで完結し、既存レコードの再暗号化を不要にした。

あわせて Issue #140 への対応として、PBKDF2の反復回数（`kdfIterations`）と暗号化スキームのバージョン（`cryptoVersion`）をレコード単位（family単位）でスキーマ管理し、将来イテレーション数を引き上げても旧パラメータで作成された既存データを復号可能にした。

## Alternatives

- **単一の派生鍵で全レコードを直接暗号化する（マスターキー層を持たない2層構造）**：これは Issue #138 以前の実装が実際に採用していた方式であり、仮説上の代替案ではない。パスコード変更のたびに全レコードの再暗号化（O(n)）が発生し、家族の保有レコード数が増えるほど変更コストが線形に増大するという実際の課題があったため、Issue #138 でマスターキー層を追加する形に置き換えられた。
- **メンバーごとの非対称鍵ペア（公開鍵で共有データを暗号化する方式）**：メンバー単位でのアクセス取り消し（暗号学的な除名）が可能になる利点はあるが、鍵配布・端末紛失時の鍵再発行・実装複雑度が本プロジェクトの規模に対して過大と判断し、将来検討事項として見送った。
- **固定の反復回数をハードコードし、スキーマ管理しない**：実装は単純だが、将来イテレーション数を引き上げる際に全ユーザーの再ログイン・再暗号化を一斉に強制する必要が生じるため、Issue #140 で family 単位のスキーマ管理に変更された。

## Consequences

- パスコード変更はマスターキーの再ラップのみで完了し、O(1)で済む（`families.rotatePasscode`、Issue #138）。
- 一方、家族グループ自体を移る「家族移行」はマスターキーが変わるため、各レコードのDEKを再ラップするO(n)の処理が必要になる。現時点では、チャンク（バッチ）単位の処理と楽観的ロックによる競合制御（Issue #174, #190、いずれもclosed）として実装されている。
- **未実装の拡張として**、処理途中の通信断・タブクローズ等からのより堅牢な中断・再開を目的とした、Web Worker + IndexedDB ベースの専用アーキテクチャ（Issue #111）が計画されているが、本稿執筆時点では open（未着手/未完了）であり、まだ実装されていない。
- 家族パスコードは全メンバー共有であり、特定メンバーだけを暗号学的に締め出す（過去に見えたデータへのアクセスを取り消す）ことはできない。メンバーの除名は認可層（`familyId`のつけ替え）でのみ制御され、暗号学的な取り消しではないという明確なトレードオフがある。
- 反復回数の引き上げは family 単位で段階的に行うことができ、全ユーザー一斉のマイグレーションを強制しない（Issue #140）。

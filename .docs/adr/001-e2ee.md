# ADR-001: E2EE Architecture

## Status

Accepted（事後的に整理したADR。特定の単一Issueに紐づく決定ではなく初期設計判断だが、この境界の妥当性はIssue #2「平文をサーバサイドで扱ってないかチェック」（closed）で確認されている）

## Context

PoohMa は家族間でアカウントのパスワードヒントを共有するアプリである。サーバー（Convex）が侵害された場合でも、パスワードヒントの平文が漏洩しないことを保証したい。一方で、サービス名検索・タグ絞り込み・OGP自動取得・ふりがな自動生成といった利便性機能は維持したい。

すべてのフィールドを暗号化する「フルE2EE」と、暗号化を一切行わない「サーバー信頼モデル」の間で、どこまでを暗号化対象にするかを決める必要があった。

## Decision

暗号化対象を「パスワードヒント」のみに限定する。サービス名・URL・メモ・タグ・ログインIDはサーバーに平文で保存し、パスワードヒント（`credentials[].passwordHint`）のみをクライアント側で AES-GCM 暗号化してから送信する。復号もクライアント側のみで行い、サーバーは暗号化済みの値をそのまま保存・配信する。

## Alternatives

- **全メタデータのE2EE**：検索・ソート・タグ絞り込みができなくなる、OGP・ふりがな自動取得機能と両立が難しくなる、実装・デバッグコストが大幅に増える。守るべき資産（パスワード関連情報）に対して過剰な対策になると判断し不採用。
- **サーバー側暗号化（保管時暗号化のみ、鍵はサーバーが保持）**：実装コストは最小だが、サーバー侵害時に鍵ごと漏洩し、E2EEとしての保証を提供できない。想定する脅威（サーバー侵害による平文開示）に対して無効なため不採用。
- **暗号化なし（メタデータと同様に平文保存）**：実装が最も単純だが、最も守りたい情報（パスワードのヒント）が無防備になるため不採用。

## Consequences

- パスワードヒントはサーバー側で検索・ソート・全文検索の対象にできない。
- パスコードを忘れた場合、サーバー側に平文のバックアップが存在しないため、専用のリカバリー経路（ADR-003）が必須になる。
- サービス名・URL・メモ・タグ等のメタデータは暗号化対象外であり、これらの情報自体が漏洩した場合の防御はE2EEの範囲外（認可・アクセス制御側の責務、ADR-004）となる。

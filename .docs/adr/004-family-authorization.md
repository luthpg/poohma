# ADR-004: Family Authorization

## Status

Accepted（Issue #137, #132, #159, #166, #167 を実装の裏付けとして参照し、事後的に整理したADR。Issue #160 は関連する対応中の拡張として言及するが、本稿執筆時点では未完了（open）である）

## Context

初期の実装では、サービスレコードの所有権判定にフルテーブルスキャンを伴う方式を採用しており、パフォーマンスとスケーラビリティの両面で課題があった。この課題は Issue #137「Convex のフルテーブルスキャン廃止 + サービスレコードの所有権をDrive型ACLモデルへ移行する」として明示的に対応されている。

また、招待の仕組みについても、招待コードを知るだけで即座に家族に参加できてしまう場合のリスク（招待リンク漏洩がそのまま不正参加に直結する）が課題となり、Issue #132「有効期限付きの家族招待コードの導入」として対応された。

## Decision

Issue #137 への対応として、所有権モデルを Google Drive に類似した「Drive型ACLモデル」へ移行した。`ownerType`（`"user"` | `"family"`）、`ownerFamilyId`、共有時のみ意味を持つ`admins`配列を導入し、インデックス（`by_ownerType_accountId` / `by_ownerType_ownerFamilyId`）による効率的なクエリでフルテーブルスキャンを廃止した。この所有権モデルの検証を`rls.ts`の`requireContentAccess`/`requireAdminAccess`に集約する。

あわせて、`customBuilders.ts`に3段階のConvexカスタムビルダー（`identityVerifiedQuery/Mutation` → `authenticatedQuery/Mutation` → `familyBoundQuery/Mutation`）を用意し、生の`query`/`mutation`を直接エクスポートしない規約とした。

Issue #132 への対応として、招待は「有効期限付きの招待コードによる参加申請」と「既存メンバーによる承認」を分離した二段階フローとした。

## Alternatives

- **フルテーブルスキャンに依存した所有権判定の継続**：Issue #137 以前の実装が実際に採用していた方式であり、仮説上の代替案ではない。データ量の増加に伴いパフォーマンスが劣化するため置き換えられた。
- **各関数内に都度アクセス制御コードを個別実装**：柔軟だが、実装漏れ（チェック忘れ）による認可バグのリスクが高く、レビューコストも増大するため不採用。
- **招待コード＝即時参加（有効期限なし・承認不要）**：Issue #132 以前の状態に近い想定。招待コードが漏洩した場合に第三者がそのまま家族データへアクセスできてしまうリスクがあるため、有効期限と承認制を導入した。
- **本格的なRBAC（ロール・権限管理）フレームワークの導入**：家族内の役割は実質的に「所有者/管理者」と「一般メンバー」程度であり、汎用RBACフレームワークの導入は本プロジェクトの規模に対して過剰と判断し不採用。

## Consequences

- 認可の正しさは、新規に追加するConvex関数が適切なビルダーを選択するという開発規約に依存しており、型システムやLintによる機械的な強制ではない。この点は Issue #166「users.ts / 認証・認可ロジックの専用テストを拡充する」（closed）、#167「重要な認可ロジックを高カバレッジ閾値の対象へ追加する」（closed）として、テストによる担保を強化する方向で対応済みである。
- Drive型ACLモデルへの移行により、インデックスを用いたクエリが可能になった一方、所有権判定のロジック自体はアプリケーションコード側に存在し続けるため、Issue #159「Convex ACL / Authorization Integration Testを拡充する」（closed、対応済み）による回帰防止に加え、Issue #160「E2EE / WebAuthn主要フローのBrowser E2Eテストを追加する」（open、対応中）によるさらなるカバレッジ拡充が計画されている。
- 招待コード漏洩のみでは家族に参加できず、既存メンバーの承認が必ず必要になるため、不正参加のハードルが上がる一方、正規の参加者にとっても承認待ちのワンステップが増える。

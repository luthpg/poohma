# ADR-003: Recovery

## Status

Accepted（Issue #134「致命的なデータ喪失を防ぐ『リカバリーキット（復元コード）』の発行」を実装の裏付けとして参照し、事後的に整理したADR）

## Context

E2EEを採用した結果（ADR-001, 002）、家族パスコードを完全に忘れた場合、サーバー側にはそれを復元する手がかりが一切ない。「サーバーは平文を知らない」という保証と、「ユーザーがロックアウトされて二度とデータにアクセスできなくなる」という事態のバランスを取る必要があり、これは Issue #134 として明示的に対応された。

## Decision

Issue #134 への対応として、発行時に一度だけ提示される高エントロピーなリカバリーコード（サーバー非保存）と、登録メールアドレス宛の6桁Email OTP（ハッシュ保存、10分有効、5回試行、60秒間隔）を組み合わせた2要素のリカバリー経路を導入した。リカバリーコードは、パスコード経路とは別に同一のマスターキーへ到達する第二のラップ経路（`recoveryMasterKeyEncrypted`）として設計する。

## Alternatives

- **秘密の質問（セキュリティクエスチョン）方式**：推測・SNS等からの情報収集による総当たりに弱く、E2EEを採用した意味を損なうため不採用。
- **サーバー管理者によるパスコードリセット（バックドア）**：実装は容易だが、「サーバーはパスワードヒントを復元できない」というE2EEの根本的な保証を破壊するため不採用。
- **Email OTPのみ（リカバリーコードなし）**：メールアカウントが侵害された場合に単一要素で復元できてしまい、E2EE鍵への到達点としては要素が1つでは不十分と判断し不採用。
- **家族メンバーによる承認のみでの復元（ソーシャルリカバリー）**：他メンバーがマスターキーの鍵材料を保持していない設計（ADR-002）のため、暗号学的にメンバー間で鍵を再構成する仕組みが別途必要になり、今回のスコープでは見送った。

## Consequences

- リカバリーコードと登録メールアドレスの両方に同時にアクセスできなくなった場合、設計上、家族はデータを復元できない（サーバー側に救済手段がないことがE2EEの前提そのものであるため）。ユーザーにリカバリーキットの安全な保管を促す必要がある。
- リカバリーコードの再発行のたびに旧リカバリー経路は完全に無効化されるため、複数端末でリカバリーキットを使い回す運用はできない。

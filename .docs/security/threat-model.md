# PoohMa 脅威モデル

## 0. 本書について

本書は、PoohMaが「何を守り、何を守らないか」を明文化したドキュメントである。要件定義書・設計書が「何を作るか」を定義するのに対し、本書は「その設計が、誰からの、どのような攻撃に耐えられるのか／耐えられないのか」を明らかにする。開発者が新機能追加時に無自覚にセキュリティ保証を壊さないためのガイド、およびユーザー向けヘルプ文言の情報源として用いる。

## 1. 保護対象資産（Assets）

| 資産 | 機密度 | 備考 |
| --- | --- | --- |
| パスワードヒント（`credentials[].passwordHint`） | 高 | E2EEで暗号化される唯一の「秘密情報」本体 |
| マスターキー・DEK（展開状態） | 高 | 保護対象そのものではないが、これが漏れるとヒントが全て復号される |
| 家族パスコード | 高 | サーバー・ブラウザいずれにも保存されないが、知られると全ヒントが復号可能になる |
| サービス名・URL・メモ・タグ・ログインID | 中 | 暗号化されず平文でサーバーに保存される（後述） |
| ユーザーのメールアドレス・表示名・プロフィール画像 | 中 | Firebase Authが管理するPII |
| 家族の構成情報（メンバー一覧、招待コード） | 中 | 誰が誰と家族グループを組んでいるかという関係性情報 |

## 2. 信頼境界（Trust Boundaries）

PoohMaの暗号化アーキテクチャは、3つの信頼領域にまたがる（詳細は暗号化アーキテクチャ図を参照）。

- **頭の中**：家族パスコードのみが存在する。最も信頼されるが、システムが直接制御できない領域。
- **ブラウザ（クライアント端末）**：展開済みマスターキー、平文ヒント（表示・編集中のみ）が一時的に存在する。ユーザーの端末・ブラウザの健全性に依存する。
- **サーバー（Convex・関連SaaS群）**：暗号化済みデータと、平文のメタデータ（後述）が永続化される。運用者・インフラ事業者を信頼する必要がある領域。

## 3. 攻撃者モデル（誰から守るか）

| ID | 攻撃者 | 想定シナリオ |
| --- | --- | --- |
| T1 | サーバー側の攻撃者（DB侵害・内部不正・バックアップ流出） | ConvexのDBダンプや、運用者アカウントの侵害により全データを閲覧できる状態 |
| T2 | ネットワーク上の攻撃者（MITM） | 通信経路上でのパケット盗聴・改ざん |
| T3 | XSS攻撃者（ブラウザ内でのスクリプト実行） | 何らかの手段でPoohMaのオリジン上で任意のJSを実行できる状態 |
| T4 | 端末レベルの攻撃者 | マルウェア、ロック解除済み端末の盗難・のぞき見（ショルダーハッキング） |
| T5 | オフライン総当たり攻撃者 | 何らかの経路でmasterKeyEncrypted等の暗号文とソルトを入手し、パスコードを推測しようとする |
| T6 | 家族メンバー（正規権限の濫用） | 正規に家族グループへ参加したメンバーが、共有設定（`ownerType: "family"`）のレコードを閲覧・悪用する |
| T7 | 第三者サービス自体の侵害 | Firebase / Resend / microCMS 等、PoohMaが信頼して利用しているSaaS自体の侵害 |
| T8 | マルチアカウント間のクロスアカウント・データ侵害（IDOR・鍵混用・キャッシュ漏洩） | 同一端末・同一ブラウザで複数アカウントを切り替えて利用する際のアカウント間データ混用・認可漏れ |
| T9 | 招待コードの漏洩（悪意のある第三者への流出） | 共有された招待リンクやQRコードが第三者に傍受・流出し、不正な参加申請が試みられる |
| T10 | リカバリーキット（PDF・復元コード）の盗難・流出 | 物理印刷されたPDFや保存コードが第三者に盗難・閲覧され、マスターキーの不正復元が試みられる |

## 4. 脅威ごとの防御と残存リスク


### T1: サーバー側の攻撃者（DB侵害）

- **防御**：パスワードヒントはエンベロープ暗号化されており、DBダンプを取得してもパスコードなしでは復号不可能（NFR-SEC-01, 02, 03）。マスターキー・DEKも常に暗号化された状態でのみ保存される。
- **残存リスク**：サービス名・URL・メモ・タグ・ログインID・ユーザーのメールアドレス・家族構成は暗号化対象外であり、DB侵害時にはこれらが平文で漏洩する。これは「パスワードそのものではなく、ヒントを守る」というPoohMaの設計思想上の意図的な非対象であり、脆弱性ではない。ただし、ユーザーへの説明責任として明示する必要がある。

### T2: ネットワーク上の攻撃者（MITM）

- **防御**：全通信はHTTPS/TLS（Vercel・Convexともに標準で提供）を前提とする。
- **残存リスク**：TLS終端後（サーバー内部・SaaS間連携）の盗聴は本モデルの対象外（各SaaS事業者の責任範囲）。

### T3: XSS攻撃者

- **防御**：
  - ユーザー入力値はReactのデフォルトエスケープにより自動エスケープされる
  - microCMS由来のリッチテキスト（CmsRichTextコンポーネント）は、許可されたHTMLタグのallowlist（h2, h3, p, code, ul, li, strong, em, a, br）に基づき、それ以外のタグを除去する基本的なサニタイズを実施
  - リンク（a要素）のhref属性は、http/https/mailtoスキームのみを許可し、javascript:等の危険なスキームを除外
  - インラインイベントハンドラー（onclick, onerror等）を除去
  - `apps/web/src/start.ts` のサーバーミドルウェアにより、全GETリクエストに対してnonceベースの厳格なCSP（`default-src 'none'`, `script-src 'strict-dynamic' 'nonce-...'`, `frame-ancestors 'none'`）およびセキュリティヘッダー（`X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`）を適用済み（Issue #128）
- **残存リスク**：**PoohMaのE2EEは「ブラウザのJS実行環境が健全であること」を前提としている。** XSSが成立した場合、攻撃者は展開済みのマスターキー・画面表示中の平文ヒントを直接窃取できる。E2EEはサーバー側の攻撃者からは保護するが、クライアント側のコード実行を奪われた場合は無力化される。現行のCSPおよびallowlistベースサニタイズはこのリスクを大幅に軽減するが、ブラウザ拡張機能や端末マルウェアを含む完全なクライアント環境侵害を防ぐものではない。

### T4: 端末レベルの攻撃者

- **防御**：無操作時のオートロック（マスターキーをメモリから破棄）を実装済み。生体認証はローカル端末のセキュア領域に依存する。
- **残存リスク**：ロック解除済みの端末を物理的に奪われた場合、その場でヒントを閲覧されることは防げない。マルウェアによる端末そのものの侵害（キーロガー、メモリダンプ等）も対象外。OSレベルの端末ロック・端末セキュリティは利用者自身の責任範囲とする。

### T5: オフライン総当たり攻撃者

- **防御**：鍵導出にPBKDF2（SHA-256、30万回）を使用し、総当たりのコストを高めている。さらにパスコード作成時の複雑性チェック（@zxcvbn-tsによるスコア2以上・最低10文字）および誤入力時の指数バックオフ・一時ロックアウトを適用している。イテレーション数および暗号化スキームバージョンは`families`テーブルでスキーマ管理され（NFR-SEC-14）、将来的なパラメータ引き上げ時も旧データとの後方互換性を担保する。
- **残存リスク**：パスコード強度要件（NFR-SEC-13）、総当たり遅延（FR-CRYPT-04）、PBKDF2反復回数のスキーマ管理・後方互換性（NFR-SEC-14）により大幅に緩和済み。

### T6: 家族メンバーによる正規権限の濫用

- **防御**：所有モデル（`ownerType: "user"` / `ownerType: "family"`）および管理者権限（`admins`）により、個人レコードを家族内でも非公開にできるほか、共有レコードの勝手な削除や共有解除は管理者に制限される。メンバーの除名（キック）時は `users.familyId` が即時クリアされ、Convex RLSにより旧家族の全レコードへのアクセス権が即座に遮断される。また、キックされたユーザーの個人所有レコード（`ownerType: "user"`）は `pendingExportVaults` を介して安全に新家族へ持ち出せる一方、家族共有レコード（`ownerType: "family"`）は家族資産として旧家族に残存し持ち出せない。
- **残存リスク**：PoohMaの家族グループは「相互に信頼し合う関係」を前提としたモデルであり、共有レコード（`ownerType: "family"`）の閲覧・編集は家族メンバー全員に許可される。共有設定にした時点で、そのレコードは家族の誰か一人にでも閲覧されうる。また、キックされた元メンバーは頭の中に「旧家族のパスコード」を記憶している可能性がある。RLSによりConvex DBへのアクセスは遮断されるが、過去にローカルキャッシュ等を取得されていた場合の復号や将来のリスクを完全に排除するため、キック完了直後に残存メンバーに対してパスコードローテーション（`FR-FAM-10`）の実施を強く推奨するUI・運用を設けている。パスコードがローテーション（再暗号化）されると、旧パスコードは完全に無効化される。

### T7: 第三者サービス自体の侵害

- **防御**：各SaaSへの認証情報（APIキー等）は環境変数として管理し、内部API（`getUserByFirebaseUid`）は共有シークレットで保護している（NFR-SEC-08）。
- **残存リスク**：Firebase Authentication自体が侵害された場合、なりすましログインのリスクがある（ただしE2EEデータの復号にはパスコードが別途必要なため、ヒント自体の即時漏洩には直結しない）。Resend・microCMSの侵害は、それぞれメール送信内容の窃取・公開コンテンツの改ざんに限定され、E2EEデータへの影響はない。また、E2Eテスト用に、Firebase Admin SDKでカスタムトークンを発行し実Google認証をスキップする専用テストユーザー（`E2E_TEST_UID`）をステージング環境にのみ用意している。本番Convexデプロイ・本番ユーザーデータとは分離されており、対応するサービスアカウントは最小権限（Firebase Authentication管理のみ）に絞る。

### T8: マルチアカウント間のクロスアカウント・データ侵害（IDOR・鍵混用・キャッシュ漏洩）

- **防御**：
  - **IDOR（アカウント偽装）の防止**：Convexの `customBuilders.ts`（`resolveAccount`）にて、リクエストされた `accountId` の所有者（`user.userId`）が認証コンテキストの `identity.subject` と一致することを必ず検証し、他人の `accountId` の指定は `Unauthorized` 例外で拒否。
  - **レコード所有権の分離**：`serviceRecords` テーブルに `accountId` フィールド（`Id<"users">`型）および `ownerType` を保持し、個人レコードの所有権判定を Firebase UID (`userId`) ではなくアカウント ID (`accountId`) 単位で実施。RLS（`convex/rls.ts`）および全クエリ・削除処理で `record.ownerType === "user" && record.accountId === user._id` による厳密な照合を強制。同一 Firebase UID を共有する別アカウント間でも、個人レコードは互いにアクセス・変更・削除不可。共有レコードの削除・管理者操作も `admins` に含まれるアカウントのみに制限。
  - **E2EE境界と鍵の破棄**：フロントエンド（`PasscodeProvider`）にて、アカウント切り替えが発生した瞬間に前アカウントの MasterKey を揮発性メモリから即時破棄し、再パスコードロック状態へ遷移。
  - **キャッシュの分離**：アカウント切り替え時に `clearQueryCache()` と `queryClient.invalidateQueries()` を連動実行し、IndexedDB/TanStack Query キャッシュの残留・混用を防止。
  - **ファミリー境界の隔離**：Convex RLS（`convex/rls.ts`）およびインデックス（`by_family_sortKey`）にて `familyId` によるデータ境界を強制。
- **残存リスク**：アカウント切り替え時にユーザー自身が同一パスコードを複数ファミリーで使い回している場合、片方のファミリーのパスコード漏洩が他方へ波及するリスクがある（ユーザー運用上の注意喚起が必要）。

### T9: 招待コードの漏洩（悪意のある第三者への流出）

- **防御**：
  - **家族IDからの分離**：招待コードは恒久的な家族ID（`families._id`）から完全に分離し、`familyInvites` テーブルにて暗号学的に安全なランダム文字列（UUID）として発行。
  - **有効期限（TTL）と手動失効**：招待コードには有効期限（15分〜30日）が必須であり、家族メンバーはいつでも即座に手動失効（`revokedAt`）させることが可能。期限切れまたは失効済みのコードによる参加申請・情報照会はサーバー側で厳格に拒否。
  - **二重の防御（承認制）**：招待コードはあくまで「参加申請を送信する権利」を与えるものに過ぎず、家族への正式参加・マスターキーへのアクセスには既存家族メンバーによる明示的な承認が必須。
  - **監査証跡**：どの招待コード経由で参加申請が行われたかを `joinRequests.invitedByCode` に記録し、使用回数（`useCount`）を追跡可能。
### T10: リカバリーキット（PDF・復元コード）の盗難・流出

- **防御**：
  - **2要素認証の必須化（FR-CRYPT-07）**：リカバリーコード単体ではマスターキーの復元は成立せず、登録メールアドレスへのワンタイム認証コード（Email OTP: 6桁数字）の検証が必須。
  - **OTPの保護とレート制限**：OTPは平文でDB保存されずSHA-256ハッシュで管理。有効期限（10分）、最大試行回数（5回で即時失効）、および60秒インターバルの再送信レート制限を適用。
  - **再発行時の即時無効化（FR-CRYPT-08）**：リカバリーキット再発行時は、旧Recovery暗号情報をDBから完全上書き・破棄し、旧Recovery Codeを即座に無効化。
  - **発行・再発行・パスコード変更の家族通知**：リカバリーキットの発行・再発行時、およびパスコード復元更新時は家族メンバー全員へ即時通知メールを送信。
- **残存リスク**：攻撃者が物理的なリカバリーキットPDF（Recovery Code）と、ユーザーの登録メールアカウントの両方を同時に完全に掌握した場合に限り復元が成立する。

## 5. 明示的に「守らない」こと（非対象の宣言）

- **実際のパスワードそのもの**：PoohMaはそもそも実パスワードを入力・保存する機能を提供しない。ユーザーが誤ってヒント欄に実パスワードを入力した場合、暗号化はされるが、これはPoohMaの設計が防げる範囲外のユーザー操作である。
- **メタデータの機密性**：サービス名・URL・メモ・タグ・ログインID・家族構成は暗号化されず、サーバー上で平文管理される。
- **クライアント実行環境の健全性**：ブラウザ・OS・拡張機能が悪意を持たないことを前提とする。XSSやマルウェアによるクライアント側の侵害はE2EEの保護範囲外。
- **物理的な端末セキュリティ**：ロック解除済み端末の盗難・のぞき見からの保護は、オートロックによる時間的な緩和にとどまる。
- **家族メンバー間の相互不信への対応**：家族メンバーは互いを信頼する関係にあることを前提とし、メンバー間の権限分離・監査証跡による抑止（FR-REC-16等）は提供するが、悪意あるメンバーによる共有データ（`ownerType: "family"`）の閲覧そのものを技術的に阻止することはできない。
- **パスコード・リカバリーキー双方の喪失時のデータ復旧**：E2EEの設計上、両方を紛失した場合のデータは復旧不能である。これは欠陥ではなく、サーバー側に復号手段を残さないという設計そのものの帰結である。

## 6. 開発者向けの安全な実装原則

- 新しいConvex関数を追加する際は、必ず `customBuilders.ts` の `authenticatedQuery` / `familyBoundQuery` 等を経由し、生の `query` / `mutation` を直接エクスポートしない。
- サーバー側のログ・エラーメッセージに、復号後の平文ヒントやマスターキーを出力しない。
- 新しいフィールドを `serviceRecords` 等に追加する際は、「これはE2EE暗号化すべき秘密情報か、平文メタデータとして許容できる情報か」を必ず明示的に判断し、本書またはコードコメントに記録する。
- ユーザー入力を `dangerouslySetInnerHTML` 等でHTMLとして描画しない。CMS由来のリッチテキストは、CmsRichTextコンポーネントのallowlistベースサニタイズを経由して描画する。新しいHTMLタグを許可する場合は、XSS攻撃ベクトルとなりうる要素（script, iframe, object, embed等）でないことを確認し、ALLOWED_TAGSへの追加理由を明記する。
- microCMS側でリッチテキストエディタの設定を変更する場合は、追加されるHTMLタグがCmsRichTextコンポーネントのallowlistに含まれているか確認する。
- 暗号化・認可ロジックへの変更は、対応するテスト（`tests/convex-users.spec.ts`, `tests/convex-recovery.spec.ts` 等）の追加・更新を伴わない限りマージしない。

## 7. 既知の残存リスクと今後の対応（要件定義書との対応）

| 残存リスク | 対応する要件ID | 状態 |
| --- | --- | --- |
| XSS成立時にマスターキーが無防備になる | NFR-SEC-12（CSP導入） | 対応済み（`start.ts` サーバーミドルウェアによる nonce ベース厳格 CSP・セキュリティヘッダー適用） |
| パスコードの複雑性チェックがない | NFR-SEC-13 | 対応済み（@zxcvbn-tsによる強度判定・メーター導入、最低10文字＆スコア2以上） |
| パスコード入力の無制限再試行によるオフライン総当たり攻撃 | FR-CRYPT-04（指数バックオフ・ロックアウト） | 対応済み（3回以上連続誤入力時の指数バックオフおよび一時ロックアウト実装） |
| PBKDF2反復回数を将来引き上げる際の後方互換性 | NFR-SEC-14 | 対応済み（`families.kdfIterations` / `families.cryptoVersion` によるスキーマ管理とフォールバック実装） |
| パスコード・生体認証端末を両方失った場合のデータロスト | FR-CRYPT-06, 07, 08（リカバリーキット・2FA復元） | 対応済み（PDF発行、Google Drive/ローカル保存/印刷、Email OTP 2段階復元） |
| OGP取得機能を悪用したリソース枯渇（DoS） | NFR-SEC-11 | 対応済み（リダイレクト上限10回・5MBサイズ制限・5秒タイムアウト・循環検知を `fetchSafeBuffer` で実装） |

本表は要件定義書の更新に合わせて随時見直すこと。

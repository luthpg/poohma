# 家族間アカウント管理アプリ「PoohMa」要件定義書

**プロジェクト名:** PoohMa (プーマ)
**バージョン:** 2.0.0
**最終更新日:** 2026/08/09

## 0. 本書について

### 0.1 目的

本書は、家族間アカウント管理アプリ「PoohMa」プロジェクトについての要件をまとめたものである。

### 0.2 対象読者

- プロダクトオーナー、企画担当者
- 新規参画エンジニア、QA担当者
- 本サービスの仕様把握を必要とする関係者

### 0.3 注意事項

- コードと矛盾する外部ドキュメントが存在する場合は、実装（コード）を正とする。

## 1. サービス概要

### 1.1 サービス名

PoohMa

#### 1.1.1 読み方

プーマ

### 1.2 コンセプト

「実際のパスワードを1文字もサーバーに預けない」ことを最大の特徴とする、家族専用のアカウント情報共有サービス。
パスワードそのものではなく、家族にしか分からない「パスワードのヒント」を暗号化して共有する。

### 1.3 ターゲットユーザー（想定）

- 動画配信サービス・Wi-Fi・各種サブスクリプション等のアカウントを家族で共有している世帯
- 親子・祖父母を含む、ITリテラシーに差がある家族構成
- 「パスワードを教え合うことへの心理的抵抗」「メモの紛失リスク」を課題としているユーザー

### 1.4 提供価値（バリュープロポジション）

以下の3点を中核的な価値提案として設計する。

1. **セキュリティ** ：サーバーに保存されるのは本人が決めた「ヒント」のみ。実パスワードは保存せず、ヒント自体も暗号化され、閲覧には家族パスコードが必要。
2. **かんたん共有** ：レコード作成・共有範囲の指定がボタン一つで完結する直感的な操作性。
3. **自由（ロックインしない）** ：登録した全データをいつでもCSV/プレーンテキストとしてエクスポートし、退会できる。

## 2. 用語定義

| 用語                       | 定義                                                                                |
| ------------------------ | --------------------------------------------------------------------------------- |
| 家族グループ（Family）           | サービス利用の前提単位。ユーザーは必ずいずれか1つの家族グループに所属する（未所属時は機能利用不可）。                               |
| マスターキー（Master Key）       | 家族グループ単位で1つ生成される家族共用の暗号鍵。家族が知る「家族パスコード」から導出した鍵でラップされてサーバーに保存される。                  |
| DEK（Data Encryption Key） | 認証情報（credential）1件ごとに生成される暗号鍵。マスターキーでラップされて保存され、パスワードヒント本体の暗号化に使われる（エンベロープ暗号化方式）。 |
| 家族パスコード                  | 家族メンバー各自が入力する、マスターキーのロック解除用の合言葉（8文字以上）。サーバーには保存されない。                              |
| サービスレコード（Service Record） | 1つのWebサービス・アカウントに対応する登録単位（タイトル、URL、認証情報群、タグ等を含む）。                                 |
| 認証情報（Credential）         | サービスレコード内の、ログインIDとパスワードヒントの組。1レコードに複数保持できる。                                       |
| 可視性（Visibility）          | サービスレコードの公開範囲。 `PRIVATE` （登録者のみ閲覧可）と `SHARED` （家族全員に共有）の2値。                       |
| 参加申請（Join Request）       | 招待コードを用いて他の家族グループへの参加を申し込む処理。ステータスは pending / approved / rejected。                |
| 家族移行（Family Migration）   | ユーザーが所属する家族グループを変更（新規作成 or 他家族への参加）する処理。既存の暗号化データを新しいマスターキーで再暗号化する一連のトランザクション。    |
| OGP情報                    | 登録URLから自動取得するタイトル・画像・説明文（Open Graph Protocol）。                                    |
| ふりがな（読み仮名）               | サービス名から自動生成される読み仮名。五十音インデックス表示に利用。                                                |

## 3. 前提条件・ビジネス制約

- 利用には「家族グループ」の作成または参加が必須であり、未所属のユーザーは家族管理画面以外にアクセスできない。
- ログイン手段はGoogleアカウントのみを提供する（他のSNS/メールパスワード認証は提供予定なし）。
- サービスの設計思想として、実際のパスワードそのものを保存する機能を意図的に提供しない（「ヒント」の保存に限定する案内）。
- 暗号化・復号処理はすべてブラウザ（クライアント）側で完結させ、サーバーへは暗号化済みデータのみを送信する（E2EE）。

## 4. ユーザー種別

| 種別             | 説明                                                                |
| -------------- | ----------------------------------------------------------------- |
| 未登録訪問者         | ログイン前の公開ページ（LP、使い方、FAQ、規約等）の閲覧のみ可能。                               |
| 登録済み・家族未所属ユーザー | Googleログイン済みだが家族グループに未所属。家族の作成・参加申請のみ可能。ダッシュボードなどにはアクセス不可。        |
| 家族メンバー         | 家族グループに所属し、全機能を利用可能。家族内での役割（オーナー/一般等）の区分は存在せず、メンバー間の権限は原則フラットである。 |

## 5. 機能要件

### 5.1 認証・ユーザー管理

| ID         | 要件                                                                                                                                                                                                                    |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-AUTH-01 | Googleアカウントによるサインアップ／ログイン（iOSでのUXを加味し、Firebase Authenticationのリダイレクト方式）を提供する。                                                                                                                                         |
| FR-AUTH-02 | ログイン成功後、サーバー側でセッションCookie（httpOnly、有効期間14日間）を発行し、以後のアクセス制御に用いる。                                                                                                                                                       |
| FR-AUTH-03 | 初回・再ログイン時にユーザー情報（表示名・メールアドレス・プロフィール画像URL）をバックエンドDBへ同期する。別FirebaseID・同一メールアドレスの既存ユーザーが存在する場合は、FirebaseIDの変更とみなし、そのユーザーの過去データを新しい認証IDへ引き継ぐ。ただし、当該メールアドレスが確認済み（emailVerified）である場合に限る。表示名は `FR-AUTH-05` と競合するため、更新を行わない。 |
| FR-AUTH-04 | ログアウト機能を提供する（Firebaseサインアウト＋セッションCookie失効＋ローカルキャッシュ破棄）。                                                                                                                                                               |
| FR-AUTH-05 | 表示名を設定画面から変更できる。                                                                                                                                                                                                      |
| FR-AUTH-06 | アカウント削除（退会）機能を提供する。退会時は本人が所有する全サービスレコードを、家族共有の有無に関わらず削除し、家族グループの最後の1人であった場合は家族グループ自体も削除する。                                                                                                                            |
| FR-AUTH-07 | フォーム入力中にセッション（14日間）が失効し、保存操作が認証エラーとなった場合、入力内容を保持したまま再ログインを促し、再ログイン成功後に自動で保存処理を再開する。                                                                                                                                   |

### 5.2 家族グループ管理

| ID        | 要件                                                                                                                                                    |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-FAM-01 | 家族グループを新規作成できる（家族名の入力、パスコード8文字以上などの条件付き＋確認入力の一致チェック）。作成と同時にマスターキーを生成し、パスコード由来の鍵でラップして保存する。                                                            |
| FR-FAM-02 | 招待コード（家族ID）・招待URL・QRコードの提示により、他ユーザーを家族グループへ招待できる。QRコードは画像として保存・共有（Web Share API対応）できる。                                                                |
| FR-FAM-03 | 招待コードを持つユーザーは参加申請を送信できる。既存メンバーのいずれかが申請を承認／却下する。                                                                                                       |
| FR-FAM-04 | 参加申請は送信者側からキャンセルでき、却下された申請は本人が削除（見送りの確認）した上で再申請できる。同時に保持できる保留中の申請は1件までとする。                                                                            |
| FR-FAM-05 | 現在所属する家族グループのメンバー一覧（表示名・メールアドレス）を表示できる。                                                                                                               |
| FR-FAM-06 | 所属家族グループを変更できる（新規家族作成 or 他家族への参加）。変更時、既存の暗号化済みパスワードヒントをクライアント側で新しいマスターキーに向けて再暗号化した上でサーバーへ送信し、レコードの所属家族を一括で付け替える。                                      |
| FR-FAM-07 | 家族移行処理は「準備（PREPARED）」状態を経て「確定（COMMIT）」される2フェーズ方式とし、準備状態は作成から30分で自動失効（EXPIRED）する。ユーザーが移行前にキャンセルした場合はABORTEDとする。失効・中断した移行先の空家族グループ（メンバー0・レコード0）は自動削除する。 |
| FR-FAM-08 | 家族グループに未所属のユーザーは、家族管理画面以外の全ページで家族管理画面へ強制的にリダイレクトされる。                                                                                                  |
| FR-FAM-09 | 現在所属する家族グループのメンバー一覧から特定のメンバーを削除することができる。この場合、当該ユーザーは即時で強制的に家族変更を要求される。                                                                                |
| FR-FAM-10 | 家族グループを変更せずにパスコードのみを変更（ローテーション）できる機能を提供する。実行時、既存レコードのDEKをすべて新パスコード由来鍵で再ラップする。                                                                         |

| FR-REC-02 | URL欄からフォーカスが外れた際、登録先WebページのOGP情報（タイトル・画像・説明文）を自動取得し、未入力項目へ反映する。                                                                                                          |
| FR-REC-03 | サービス名欄からフォーカスが外れた際、外部API連携によりふりがなを自動取得する。                                                                                                                                |
| FR-REC-04 | 1レコードに複数の認証情報（ラベル／ログインID／パスワードヒントの組）を追加・削除できる（最大10件まで。CSV入出力の列設計と一致させる）。                                                                                                 |

| FR-REC-08 | サービス名・メモ・ログインID・ラベルによるキーワード検索、タグによる絞り込み、名前／URL／更新日時の昇順・降順での並び替えができる。タグによる絞り込みは、閲覧可能な全レコードに付与されているタグの和集合をボタン群（タグクラウド）として検索欄の下に表示し、トグル式（クリックで有効／無効を切り替え、有効なタグはハイライト表示）で行う。 |

| FR-REC-13 | 一覧のカード／リスト表示、並び替え順は、ユーザー設定としてCookieに保存され、次回アクセス時も維持される。                                                                                                                  |

### 5.4 暗号化・パスコードロック

| ID          | 要件                                                                                              |
| ----------- | ----------------------------------------------------------------------------------------------- |
| FR-CRYPT-01 | 家族グループごとに1つのマスターキーを生成し、家族パスコードから導出した鍵で暗号化（ラップ）してサーバーに保存する。                                      |
| FR-CRYPT-02 | パスワードヒントごとに個別のDEK（データ暗号鍵）を生成し、マスターキーでラップして保存する（封筒暗号化）。パスワードヒント本体はDEKで暗号化する。                     |
| FR-CRYPT-03 | アプリの起動直後および所属家族の切替直後は暗号鍵が未展開の「ロック状態」であり、パスワードヒントの登録・閲覧・編集・エクスポート操作の際にパスコード入力ダイアログを表示してロックを解除する。 |
| FR-CRYPT-04 | 入力されたパスコードが誤っている場合はエラーメッセージを表示し、再入力できる。再試行に制約は設けない。                                             |
| FR-CRYPT-05 | 展開されたマスターキーはブラウザのメモリ上にのみ保持し、永続化しない（再読み込みや家族切替で消去される）。                                           |
| FR-CRYPT-06 | パスコード忘却時にマスターキーを再アンラップできる「リカバリーキー（復元コード）」を発行し、QRコード付きのA4印刷用PDFとして出力できる機能を提供する。                  |

### 5.5 生体認証

| ID        | 要件                                                                                 |
| --------- | ---------------------------------------------------------------------------------- |
| FR-BIO-01 | 対応端末では、WebAuthn（プラットフォーム認証器、PRF拡張）を用いて家族パスコードを端末内に暗号化保存し、指紋／顔認証によるロック解除を提供する。      |
| FR-BIO-02 | パスコード入力ダイアログにて「次回から指紋／FaceIDでロック解除する」を選択することで生体認証を登録できる。                           |
| FR-BIO-03 | 生体認証登録済みの場合、パスコード入力の代わりにワンタップで認証・ロック解除できる。                                         |
| FR-BIO-04 | 設定画面から、当該端末に保存された生体認証データを削除（解除）できる。                                                |
| FR-BIO-05 | 生体認証に対応していない端末では、登録フローの開始前に対応状況を確認する。非対応の場合はエラーで中断せず、案内メッセージとともにパスコード入力へ自動的に切り替える。 |

### 5.6 CSVインポート／エクスポート

| ID        | 要件                                                                                                                                                               |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-CSV-01 | 自分が所有する全サービスレコードをCSV形式でエクスポートできる。認証情報もすべてまとめてサービスアカウント1つに対して1行おする（最大10件まで欠落なく出力し、上限を超えるレコードがある場合はエクスポート前に警告を表示する）。パスワードヒントは復号した上で出力する（暗号化用の内部データ：IV・DEK等は出力しない）。 |
| FR-CSV-02 | CSV出力時、セル内容が `=` `+` `-` `@` 等で始まる場合はスプレッドシートソフトでの数式実行を防ぐエスケープ処理を行う（CSVインジェクション対策）。                                                                              |
| FR-CSV-03 | CSVファイルからのインポートができる。1回あたり最大500行、各フィールド最大10,000文字までとする。                                                                                                           |
| FR-CSV-04 | インポート時、URL・サービス名が入力されている行についてはOGP情報・ふりがなを自動補完する。                                                                                                                 |
| FR-CSV-05 | インポートするパスワードヒントは、クライアント側で暗号化してからサーバーへ送信する。                                                                                                                       |
| FR-CSV-06 | インポート結果として、成功件数と行ごとの失敗理由の一覧を表示する。                                                                                                                                |
| FR-CSV-07 | CSVインポート時、既存データとの突合により「新規／上書き／スキップ」の判定結果を、インポート確定前にプレビュー表示する。                                                                                                    |

## 6. 非機能要件

### 6.1 セキュリティ要件

| ID         | 要件                                                                                                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| NFR-SEC-01 | 実際のパスワードそのものはシステム上いかなる場所にも保存しない（保存対象は「ヒント」に限定する設計思想）。ただしユーザーが入力する「ヒント」は暗号化されているため、運用管理者でもその「ヒント」が実際のパスワードでないかどうかの知得はできない。                   |
| NFR-SEC-02 | パスワードヒントはエンドツーエンド暗号化（E2EE）を採用し、サーバー・データベース管理者を含む何者もサーバー側で平文を閲覧できない。                                                                         |
| NFR-SEC-03 | 鍵導出関数はPBKDF2（ハッシュ関数SHA-256、反復回数30万回）を用い、対称暗号方式にはAES-GCM（256bit）を採用する。                                                                       |
| NFR-SEC-04 | 家族・レコード・ユーザーに関わるバックエンドAPIはすべて認証必須とし、未認証アクセスを拒否する。                                                                                           |
| NFR-SEC-05 | サービスレコードへのアクセスは「所有者本人」または「公開範囲がSHAREDかつ同一家族グループ」の場合のみ許可する制御をサーバー側で必ず行う（クライアント側の表示制御に依存しない）。                                                 |
| NFR-SEC-06 | URLからOGP情報を取得する機能はSSRF対策を実施する：スキームをhttp/httpsに限定、DNS解決したIPアドレスがプライベート／ループバック／リンクローカルの場合は拒否、リダイレクト追跡のたびに再検証、最大リダイレクト回数・レスポンスサイズ・タイムアウトを制限する。 |
| NFR-SEC-07 | CSV出力はスプレッドシートソフトでの数式実行につながる先頭文字をエスケープする（CSVインジェクション対策）。                                                                                    |
| NFR-SEC-08 | サーバー間内部API（Firebase UIDによるユーザー照会）は共有シークレットによるヘッダー認証で保護する。                                                                                   |
| NFR-SEC-09 | 生体認証関連の秘匿情報（WebAuthn資格情報ID、暗号化済みパスコード等）は端末ローカル（IndexedDB）にのみ保存し、サーバーへは送信しない。                                                                |
| NFR-SEC-10 | すべての入力値をスキーマバリデーション（文字数上限、Base64／IV形式の妥当性等）によりクライアント・サーバー双方でチェックする。                                                                         |
| NFR-SEC-11 | OGP取得処理は、リダイレクト追跡回数の上限設定やレスポンスサイズの検証・制限を行い、悪意あるレスポンスによるメモリ枯渇（DoS）を防止する。                                                                     |
| NFR-SEC-12 | CSP（Content Security Policy）等のセキュリティヘッダーを設定し、XSS発生時のデータ外部送信（マスターキー窃取を含む）を防止する。                                                              |
| NFR-SEC-13 | 家族パスコードの強度要件（最低文字数・複雑性）は、総当たり攻撃への耐性を踏まえて設定する。                                                                                               |
| NFR-SEC-14 | 鍵導出のセキュリティ強度（PBKDF2の反復回数等）を将来引き上げる場合でも、既存ユーザーの登録データが復号できなくなることがない設計とする。                                                                     |

## 8. 主要データ項目一覧（概要）

要件レベルでの主要エンティティと項目。詳細な型・インデックス定義は設計書を参照。

- **家族グループ** ：家族名、暗号化済みマスターキー、マスターキー用IV、マスターキー導出用ソルト
- **ユーザー** ：認証ID、メールアドレス、表示名、プロフィール画像URL、所属家族ID
- **サービスレコード** ：サービス名、読み仮名、URL、OGP画像／説明、メモ、公開範囲、所有者ID、所属家族ID、タグ一覧、認証情報一覧（更新日時つき）
- **認証情報** ：ラベル、ログインID、暗号化済みパスワードヒント（＋IV）、暗号化済みDEK（＋IV）
- **参加申請** ：対象家族ID、申請者ID、ステータス（pending/approved/rejected）
- **家族移行** ：申請者ID、移行元家族ID、移行先家族ID、対象レコードID一覧、ステータス（PREPARED/COMPLETED/EXPIRED/ABORTED）、有効期限

## 9. 制約事項

- ログイン手段はGoogleアカウントのみであり、他の認証方式は提供しない。
- CSVインポート／エクスポートで扱える1レコードあたりの認証情報数は、CSV列設計上、最大10件を前提としている。
- CSVインポートは1回あたり最大500行までとする（サーバー側で強制）。
- パスワードヒント・メモ等のテキスト項目には文字数上限が設けられている（メモ：10,000文字、パスワードヒント：2,000文字（登録・編集時）等）。
- 家族グループ内でのメンバー権限（オーナー／一般等）の区分は存在せず、全メンバーが同等の操作権限を持つ（参加承認・共有レコードの編集を含む）。

## 10. 今後の検討課題（実装から推測される拡張余地）

- 家族内での権限ロール分離（例：招待・削除等の操作を一部メンバーに限定する仕組み）
- 多言語対応（現状UI文言は日本語に固定）
- 複数家族（マルチ・ワークスペース）対応：1ユーザーが複数の家族グループに所属し、切り替えられるようにする案。現行は1ユーザー1家族グループを前提としている（3章・4章）ため、実現する場合は前提条件・データモデルの見直しを伴う。

# Pitfalls: PR レビュー・外部 AI 審査 & ガードレール

PR レビュー対応、外部 AI（CodeRabbit等）指摘の審査、および設計上の過剰防衛に関する落とし穴と回避法です。

---

### PR の経緯・レビュー文脈を確認せずにコード差分だけで独断判断する罠

- **問題**: PR 上で外部レビュアーから提案されたコミットの妥当性を評価する際、GitHub 上のディスカッション経緯（`gh pr view --comments`）を追わずに、コード差分だけで「仕様違反」と決めつけ、優れた改善を安易にロールバックしようとしてしまう。
- **回避法**: コード差分を見る前に必ず `gh pr view --comments` でレビュー指摘の意図・経緯を追跡し、開発ブランチの断面においてより堅牢な設計（断面最適）であれば前向きに採用する。

---

### 外部 AI（CodeRabbit 等）レビュー指摘の盲目的な鵜呑み（最重要注意点）

- **問題**:
  - CodeRabbit 等は、一般的な React / TypeScript の慣習に基づいて「catch した `error.message` をトーストで表示せよ」「すべての分岐で詳細例外を投げよ」といった提案を機械的に行う。
  - また、過去のコメントや一般的な Convex / Next.js の設定例を元に、「念のため旧環境変数（例: `APP_URL`）も優先・フォールバックとして見ておくべき」といった過剰冗長化・ゾンビコード復活の提案を行う。
  - AI エージェントがこれを盲目的に鵜呑みにして採用すると、PoohMa の最重要不変条件（[`.ai/invariants.md`](../invariants.md) 第5節: **トーストでの生エラー直接露出禁止**）や「念のため二重にする精神の排除（Single Source of Truth）」に抵触し、内部情報漏洩（CWE-209）や状態不整合、廃止済み変数のゾンビ化を招く。
- **回避法**:
  - 外部レビュー指摘を評価する際は、**必ず [`.ai/invariants.md`](../invariants.md) および Single Source of Truth の設計意図と照合して安全性を審査する**。
  - PoohMa の不変条件に反する提案（生エラー露出、暗号化省略、廃止済み変数の復活等）は、**「PoohMa の不変条件・設計方針に反するため」と明確な根拠を示して毅然と却下する**。

### マイグレーション完了前提の過剰なクライアントサイドガードコードの混入（KISS原則違反）

- **問題**:
  - スキーマ変更やデータ移行（例: `stableId` 追加）を行う際、「未バックフィルのレコードが存在したらクライアント操作（エクスポート等）を拒否して例外を投げる」といった過剰なガードをフロントエンド・Hooks に混入させてしまう。
  - これにより、本番環境でマイグレーションを実行するまでユーザー操作がブロックされ、運用が破綻する。
- **回避法**:
  - マイグレーションは「スキーマと関数を用意し、PR 中または本番リリース時に CLI（`npx convex run migrations:...`）から手動ワンショットで完了させる」運用とする。
  - クライアント側コードには過剰な未バックフィル検査ガードを設けず、`record.stableId || ""` のような自然なフォールバックで吸収する（KISS原則）。

### データインポート時の管理者・メンバー解決における過剰拒否

- **問題**: CSVインポート等で家族外メンバーが指定されていた際、即座に例外をスローして全体中断してしまうと、E2E シード投入やユーザーの既存インポートが破綻する。
- **回避法**: 家族外メンバーはエラー中断せずスキップし、インポート実行者および家族内実在メンバーを管理者に登録するフォールバック仕様に統一する。スキップされた旨はプレビュー UI の警告（コールアウト）でユーザーに明示する。

### 「念のため二重にする」精神・過剰冗長化の完全排除（思考停止の根絶）

- **問題（アンチパターンの本質）**:
  - 実装や設計時に、「念のため両方に保存しておこう」「念のため両方のレイヤーで二重チェックしよう」「念のためあっちにもこっちにも持たせておこう」と、**不安を解消する「保険」のつもりで安易に二重化する精神（マインドセット）そのものが最大の元凶**である。
  - 「何を二重にしたか（ストレージ、キャッシュ、ガード、状態管理など）」という個別事象の問題ではない。**「念のため二重にしておく」という発想自体が、ライフサイクルや責任の境界（Single Source of Truth）を突き詰める設計を放棄した思考停止**である。
- **なぜ「念のため二重にする」精神を完全に無くさなければならないのか**:
  1. **状態不整合とゾンビデータ（最大のバグ温床）**:
     - 二重に保持されたデータは、更新・同期・消去のタイミングが必ずズレる。一方を消したのに他方が残り、予期せぬデータの復活や競合、不可解なエッジケースを永久に生み出し続ける。
  2. **問題の本質と技術仕様の隠蔽**:
     - 「両方やっておけばどちらかで動くだろう」と逃げることで、本来見極めるべき「技術仕様の違い（例: 外部リダイレクト時の揮発性、コンポーネントの再マウント順序など）」の理解を怠り、真の根本原因から目を背けることになる。
  3. **保守性の破壊とコードの肥大化（KISS原則違反）**:
     - 読み取り、書き込み、検証、クリーンアップ、テストのすべてで二重の分岐が必要となり、認知負荷が倍増する。
- **徹底すべき鉄則**:
  - **「念のため」「保険」の二重化コードは1行も書かない**:
    - 「このデータのライフサイクルはどうあるべきか？」「どの層・ストレージが真の責任を持つべきか？」を論理的・技術的に突き詰め、**責任の所在（Single Source of Truth）を必ず1つに断定・一本化**する。
    - 確固たる1つの経路・責任を正しく、堅牢に機能させることに集中し、「両方やっておく」という逃げの発想を完全に根絶する。

### Artifacts（Implementation Plan等）の過去内容・前提指示の消去禁止（アーカイブ・追記の徹底）

- **問題**:
  - Implementation Plan などの artifacts を更新する際、新しい論点や派生課題に集中するあまり、過去に記載していた計画内容やユーザーからの重要指示（例:「モバイル環境でのDevTools制約」「デバッグ用コードの削除容易性」「同時編集競合との兼ね合い」等）を上書き消去してしまう。
  - その結果、コンテキストの compaction（要約）やトピック移行が発生した際に、エージェントが当初の指示や前提条件を見落とし・忘却し、重大な手戻りや指示違反を招く。
- **回避法**:
  - 別の内容や発展的論点について言及・改訂する場合でも、**過去の内容を消去せず追記するか、「アーカイブ / 履歴セクション」として明確に残した上で記載**する。
  - 当初の指示内容（制約条件、環境前提、削除方針など）を常に参照できる構造を維持し、エージェントの指示忘却を防止する。

### PR レビュー指摘対応の標準ワークフロー（分析〜Artifact方針検討〜合意後着手）

- **背景・教訓**:
  - PR レビュー（GitHub CodeQL や CodeRabbit 等の外部自動レビュー、人間レビュアーのインライン指摘など）に対して、AI エージェントが受動的・反射的にすぐプロダクションコードを改変し始めると、以下のような重大リスクが生じる：
    1. 外部 AI 指摘の誤りや過剰防衛（例: 生エラー露出、過剰な分散ロック・クレーム機構の混入）を未検証のまま取り込んでしまう。
    2. レビュー指摘が指摘している「真の事象」と「提案された解決策」を分離して吟味できない（事象は妥当でも、提案コードはアンチパターンの場合がある）。
    3. ユーザーとの設計認識や UX 方針（ボタンサイズ、レイアウト、セーフエリア対応等）の乖離が生じ、大きな手戻りとなる。
- **徹底すべき標準ワークフロー（4ステップ）**:
  1. **全指摘の網羅的収集・抽出**:
     - PR 上のインライン指摘、Nitpick コメント、Bot 警告を漏れなくリストアップし、対象ファイルと行番号を特定する。
  2. **不変条件・KISS原則に照らした妥当性精査 & ファクトチェック**:
     - 各指摘について、「指摘の事象そのものが妥当か」「提案された解決コードが PoohMa の不変条件（[`.ai/invariants.md`](../invariants.md)）や KISS 原則に合致しているか」を分離して審査する。
     - 必要に応じてブラウザ仕様（WHATWG規格、実機挙動）のファクトチェックを行い、安易な推測で設計しない。
  3. **単独の Artifact（審査報告書 & 修正計画）による可視化と方針提案**:
     - 指摘全件の一覧表、妥当性判定（採用 / 方針変更採用 / 却下）、採否根拠、および具体的な修正方針を単独の Artifact（例: `pr_xxx_review_assessment.md`）にまとめる。
     - すぐにコード変更には着手せず、**ユーザーに Artifact の確認を求めて停止（待機）**する。
  4. **ユーザー合意・フィードバック反映後の実装・動的検証**:
     - ユーザーの承認および追加フィードバック（UX調整、配置改善など）を得てから初めてプロダクションコードの修正に着手する。
     - 修正完了後は必ず `pnpm verify` および `pnpm test:e2e` で動的動作を完全検証する。

### ドキュメント群の更新漏れを防げなかった「なぜなぜ分析」と Doc-Sync Gate の鉄則

- **事象（問題の所在）**:
  - PR 改修（Issue #156 等）において、暗号化ドラフト保存・復元基盤、変更インジケーター、アクション固定フッター体験統一、BroadcastChannel タブ衝突自律回避、最低サポートブラウザ基準の明記といった大きな仕様追加・設計変更を実施した。
  - 単体テスト・E2E テスト合格や `.ai/` への知見蓄積まで完了していたにもかかわらず、ユーザーから「今回の改修全体を通じて .docs/ の修正が必要ないかはチェックしてあるよね？」と指摘されるまで、エージェント自律的には `.docs/` 公式設計書群（要件定義、機能一覧、詳細設計、デザイン仕様、セキュリティモデル等）の網羅的更新に着手できていなかった。
- **なぜなぜ分析（5 Whys）**:
  1. **Why 1: なぜコード修正・テスト完了時点で `.docs/` の更新が漏れていたのか？**
     - 「E2Eテスト合格」「レビュー指摘の解消」「`.ai/pitfalls/` への知見蓄積」に過度に意識が集中し、プロジェクト全体の公式仕様書である `.docs/` 群への横断同期が「タスク完了条件（Definition of Done）」として自動発動していなかったため。
  2. **Why 2: なぜ既存の「コミット前確認」ルール（GEMINI.md 5項）が自律的に機能しなかったのか？**
     - 「関連ドキュメントの更新要否を必ず確認する」という定性的な指示にとどまっており、レビュー対応や段階的機能拡張のループにおいて「具体的にどのタイミングで・何を契機に・どの文書を走査すべきか」という機械的なチェックリスト／ゲートが存在しなかったため。
  3. **Why 3: なぜ PR レビュー指摘対応中にドキュメント更新の意識が希薄になったのか？**
     - レビュー指摘対応を「単なるバグ修正（Bugfix / Refactor）」と狭義に捉え、レビュー対応の過程で新設・統一された仕様（固定フッター、モバイルアイコン化、最低動作環境、BroadcastChannel等）が「公式仕様書に記録すべき重要なプロダクト仕様変更」であることを見落としたため。
  4. **Why 4: なぜレビュー対応で生じた変更が「仕様書反映対象」として検知されなかったのか？**
     - `git diff --stat` を俯瞰して「新コンポーネント・新定数・新ストレージ・新UI配置・新非機能要件」を機械的に抽出し、5大設計書と突合するプロアクティブな走査プロセスを欠いていたため。
  5. **Why 5: 根本原因（Root Cause）は何か？**
     - **① 完了定義における「Doc-Sync Gate」の欠落**: 「E2Eテスト合格＝実装完了」という動的検証バイアスに陥り、ドキュメント同期を「完了後のオプショナルな作業」に転落させていたこと。
     - **② 「レビュー対応＝仕様変更」という認識不足**: レビュー対応から派生するUX改善・セキュリティ補強は仕様拡張そのものであるという意識の欠如。
- **再発防止策（3つの鉄則）**:
  1. **コミット前の「Doc-Sync Gate」の義務化**:
     - `pnpm test:e2e` 合格後、コミット直前に必ず `git status` / `git diff --stat` を行い、後述の「5大文書チェックリスト」との突合を通過することを完了の必須条件とする。
  2. **「レビュー指摘対応＝仕様拡張」マインドセットの徹底**:
     - レビュー対応で追加・変更されたUI配置、ボタン挙動、ストレージ、外部連携、環境制約は、すべて「仕様変更」として扱い、ドキュメント同期の対象とする。
  3. **5大文書マトリクスの機械的走査（チェックリスト）**:
     - `features.md`: 新機能、新UX、新連携、新環境基準の有無
     - `requirements.md`: 機能要件（FR）、非機能要件（NFR-UX, NFR-ENV）の追加・更新
     - `DESIGN.md`: コンポーネントスタイル、配置ルール、配色、トランジション、レスポンシブ仕様
     - `code-design.md`: 状態管理・ストレージ表、鍵階層、シーケンス、UI/UXガイドライン
     - `security/*.md`: E2EE境界、暗号化鍵階層、セッション、脅威モデル（T1〜T10）

### カスタムフック返却オブジェクトの useEffect 依存配列指定による参照同一性破壊（非同期処理 cleanup の罠）

- **事象（問題の所在）**:
  - `const form = useRecordForm(...)` のように、カスタムフックがレンダー毎に新しいオブジェクトリテラル（`return { values, ... }`）を返している場合、呼び出し元のコンポーネントで `useEffect(..., [..., form])` とフック返却オブジェクト全体を依存配列に含めてしまうと、コンポーネントが再レンダリングされるたびに effect の依存値が「変化した」と判定される。
  - これにより、effect 内で実行中の非同期処理（例: パスワードヒントの復号やドラフト復元）の途中で cleanup（`isCancelled = true`）が走ってしまい、完了後のステート更新（`setIsEditing(true)` 等）が不当にキャンセルされ、処理が未完了のまま放置されるバグが生じる。
- **回避法**:
  - カスタムフックの返却オブジェクト全体を `useEffect` の依存配列に渡してはならない。
  - effect 内で真に必要なプロパティやコールバック（`setBaselineValues`, `discardDraft` 等）を個別に destructure して取り出し、`useCallback` で参照が安定しているメンバーのみを依存配列に指定する。

### 非同期メタデータ取得（OGP等）における入力変更・消去時の整合性破壊とレースコンディション

- **問題（アンチパターン）**:
  - URL 等の入力値に基づいて外部メタデータ（OGPのタイトル・画像・説明文など）を非同期取得する際、取得中の Promise のみを保持して送信時や完了時に無条件に適用してしまうと、以下の重大な不整合が発生する：
    1. **送信ペイロードへの無関係メタデータの混入**: URL A の OGP 取得中に URL B へ変更、または URL を空にして即座に保存した場合、URL A の画像や説明文が URL B のレコードに保存されてしまう。
    2. **フォーム状態の不正上書き**: OGP 取得中にユーザーが入力欄をクリアまたは別 URL に変更した際、完了ハンドラが無条件に `setValues` してしまい、ユーザーの意図しない古いメタデータで上書きされる。
    3. **遅延レスポンスによるレースコンディション**: URL A blur → URL B blur と操作した際、ネットワーク遅延等で URL A のレスポンスが URL B より遅れて到着すると、最新の URL B の情報が URL A の古い情報で上書きされる。
- **回避法（ベストプラクティス）**:
  - **単調増加リクエストID（`reqIdRef`）による最新管理**: リクエスト開始ごとに ID をインクリメントし、完了時に `currentReqId === reqIdRef.current` を検証して古いリクエスト結果を確実に破棄する。
  - **開始時 URL と現在値の一致検証**: 保留中リクエストオブジェクトに `{ reqId, url, promise }` を保持し、完了時および送信ペイロード統合（`buildEncryptedPayload`）時に `targetUrl === currentUrl` であることを検証する。一致しない場合は待機せず無視・破棄する。
  - **入力変更時（`setUrl` 等）の即時無効化とクリア**: ユーザーが入力値を変更した瞬間に、進行中のリクエストを無効化（`reqIdRef += 1`, `pendingRef = null`, `isFetching = false`）し、以前の URL に付随するメタデータ（`ogpImage`, `ogpDescription`）もリセットする。

### 目先のコンパイルエラー解消を目的とした安易な `as unknown as Type` 二重キャストの禁止（思考停止キャストの根絶）

- **問題（アンチパターンの本質）**:
  - JSON インポートや外部ライブラリ連携、複雑なオブジェクトの型合わせにおいて、コンパイルエラーや型の不一致が出た際、原因を突き止めずに「目先のコンパイルを通すためだけ」に `as unknown as TargetType` という二重キャストを安易に行うこと。
  - これは TypeScript の最大の利点である静的型チェックと安全性を完全に破壊・放棄する行為であり、実行時エラーの潜在化や将来のプロパティ変更・欠落の見落としを招く最大の元凶となる。
- **なぜ安易な `unknown` キャストが起きるのか（真の原因）**:
  - 多くのケース（例: JSON ファイルインポート）では、対象データはすでに `TargetType` と完全に構造的互換性があるにもかかわらず、TypeScript の型推論の挙動（空配列 `[]` が `never[]` と推論される、JSON インポートがリテラル型のユニオンと推論される等）への無理解から、「とりあえず二重キャストで型チェッカーを黙らせる」という思考停止に陥ることが原因である。
- **回避法・徹底すべき鉄則**:
  1. **まず明示的な型注釈（Type Annotation）を適用する**:
     - `const data: TargetType[] = importedJson;` のように直接型を注釈する。TypeScript は構造的部分型（Structural Subtyping）を持つため、余分なプロパティや配列推論があっても直接代入できるケースが極めて多い。
  2. **`satisfies` 演算子を活用する**:
     - 型安全性を保証しつつ推論されたリテラル型を保持したい場合は、`const data = importedJson satisfies readonly TargetType[];` を利用する。
  3. **二重キャスト（`as unknown as T`）の原則禁止**:
     - 不可避な低レイヤー外部ライブラリ境界等を除き、プロダクションコード・スクリプト・テストにおいて `as unknown as T` による型回避を固く禁ずる。型エラーが出た場合は「なぜ型が一致しないのか（スキーマ定義の漏れ、オプショナル項目の不一致など）」を突き止め、型定義側またはデータ側を是正すること。

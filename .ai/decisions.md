# PoohMa Architecture & Design Decisions

PoohMa における重要な設計判断（Decisions）と、その現在の意味・背景を整理する。

---

## 1. バックエンド基盤: Convex (BaaS) の採用

- **判断**: リレーショナル DB + 独自バックエンドサーバー（Prisma等）ではなく、Convex（リアルタイム DB + サーバーレス関数）を採用。
- **意味**:
  - クライアントへのリアクティブなデータ同期（TanStack Query / ConvexReactClient）が標準で提供される。
  - バックエンド関数（Query / Mutation）が ACID トランザクションをネイティブに保証し、家族移行や権限変更の整合性を保ちやすい。
  - Node.js ランタイム（`actions.ts`）で OGP 取得やメール送信（Resend）等の外部連携を安全に隔離実行できる。

---

## 2. 認証方式: Firebase Authentication (Google OAuth) + セッション Cookie
 
 - **判断**: 自前のパスワード認証を持たず、Google アカウントによる Firebase Authentication（リダイレクト方式）に限定。サーバー側では httpOnly セッション Cookie（14日間）を発行。
 - **意味**:
   - パスワード管理のリスクを完全に外部化し、家族ユーザーの手軽なログインを実現。
   - Firebase Auth（IndexedDB + LocalStorage永続化）を長期ログイン状態の本体（Single Source of Truth）とし、数ヶ月単位でログイン状態を維持。
   - セッション Cookie は SSR 初期表示用キャッシュおよび補助セッションとして位置付け、利用中のトークン更新時に自動ローリング延長（`refreshSessionCookie`）。Cookie 切れのみによる強制ログアウトを防止。
   - Convex 側も `auth.config.ts` で Firebase を信頼プロバイダとして直接 ID トークンを検証。

---

## 3. 暗号化方式: E2EE (エンベロープ暗号化) & ヒント限定暗号化

- **判断**:
  - 実パスワードは一切預からず、「パスワードのヒント」のみを E2EE（Web Crypto API）で暗号化する。
  - 認証情報ごとに DEK（AES-GCM 256）を発行し、マスターキーで DEK をラップするエンベロープ暗号化を採用。
- **意味**:
  - サーバー侵害時（DB ダンプ流出）でも、パスコードなしにヒントを復号することは不可能。
  - サービス名・URL・タグ・ログインID等のメタデータは平文で保持することで、サーバー側でのインデックス検索やソート、OGP 表示の利便性を維持。
  - パスコード変更や家族移行時、ヒント本体の再暗号化が不要であり、DEK の再ラップ（軽量処理）のみで安全に完了する。

---

## 4. データアクセス制御: Drive型 ACL 所有権モデル

- **判断**: レコードのアクセス権をフラットな家族共有から、個人所有（`ownerType: "user"`）と家族共有（`ownerType: "family"` + `admins` 配列）に明確に分離。
- **意味**:
  - 個人専用のレコードを家族グループ内で非公開に保持可能。
  - 共有レコードの勝手な削除や共有解除は `admins`（管理者）に制限され、不用意なデータ消失を防ぐ。
  - `by_family_sortKey`, `by_ownerType_accountId` などの複合インデックスにより、対応するクエリでのフルテーブルスキャンを回避または削減する。ただし、すべての検索・集計・取得経路からフルスキャンを排除するものではない。

---

## 5. マルチアカウントモデル: 1 Firebase UID : N PoohMa Accounts

- **判断**: 1 つの Google ログイン（Firebase UID）に対して、複数の独立した PoohMa アカウント（`users._id`）を作成・保持できるように設計。
- **意味**:
  - 1 人のユーザーが「実家用」「配偶者用」など複数の家族グループを用途別に使い分けられる。
  - 各アカウントは完全に独立した `familyId`、familyに紐づくMasterKey、個人レコード領域を持ち、アカウント切り替え時に前アカウントの MasterKey とキャッシュを即時破棄する。

---

## 6. リカバリー設計: 2段階復元（OTP + リカバリーコード）

- **判断**: パスコード紛失時の復旧手段として、Crockford's Base32 形式のリカバリーキットを発行し、メール OTP 認証と組み合わせた 2 段階復元を採用。
- **意味**:
  - リカバリーコード平文はサーバーに保存せず（ハッシュ検証）、マスターキーはリカバリーキーで別途ラップ保存（`recoveryMasterKeyEncrypted`）。
  - OTP 検証（本人のメールアドレス到達確認）とリカバリーコード入力（物理キット所持確認）の両方が揃った場合のみ、ワンタイムセッショントークンを発行して新パスコードで再ラップを許可する。

---

## 7. 生体認証 (WebAuthn PRF) のスコープ限定

- **判断**: WebAuthn PRF 拡張は「ローカル IndexedDB 内の家族パスコード暗号化」にのみ使用し、サーバー認証やマスターキー導出には直接使わない。
- **意味**:
  - 生体認証非対応端末や Safari / Chrome 等の挙動差分があっても、コアの暗号化・認証ロジックに影響を与えず、手動パスコード入力への Graceful Fallback が容易。

---

## 8. バックアップ基盤: Cloudflare Workers + R2

- **判断**: Convex 外部の独立したバックアップ基盤として Cloudflare Workers（Cron トリガー）と R2（S3 互換ストレージ）を採用。
- **意味**:
  - Convex Cloud の障害や誤操作に備え、暗号化済みデータを第三者クラウドへ定期的に自動エクスポート・保管する。

---

## 9. 鍵導出関数 (KDF): PBKDF2 (Web Crypto API) の採用と Argon2id の見送り

- **判断**: パスコードからの鍵導出に Argon2id（Wasm/JS）ではなく、ブラウザ標準の Web Crypto API（PBKDF2-SHA256、300,000回）を採用（ADR-006）。
- **意味**:
  - Web Crypto API 標準外である Argon2id の導入に伴うバンドルサイズ増大（Wasmバイナリ）、厳格な CSP（nonce-based strict CSP）との摩擦、モバイル・低スペック端末でのメモリ圧迫・クラッシュリスクを回避。
  - バンドルサイズ 0KB かつ全モダンブラウザでの安定動作を優先。
  - GPU 総当たり耐性のトレードオフは、パスコード強度要件（zxcvbn）、指数バックオフ、反復回数のスキーマ管理（将来の移行パス確保）によって多層防御する。
